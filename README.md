## 🛠️ 如何参与项目

项目采用 GitHub 的协作方式进行开发。

### 1. 创建自己的开发分支

不要直接修改 `main` 分支。

开发新功能时，可以创建类似下面的分支：

```text
feature/xxx     # 新功能
fix/xxx         # Bug 修复
refactor/xxx    # 代码重构
docs/xxx        # 文档、README 等修改
```

例如：

```text
feature/add-club-introduction
fix/mobile-layout
docs/update-readme
```

**一个分支尽量只负责一个独立任务**，不要把多个无关修改放在同一个分支中。

同时，新建分支前请确保自己基于最新的 `main` 分支进行开发。

---

### 2. 修改项目并提交

完成修改后，使用规范的 Commit 信息。

格式：

```text
类型: 简短描述
```

常用类型：

```text
feat: 新增功能 / 页面
fix: 修复 Bug
docs: 修改文档、文案、注释
refactor: 代码重构
style: 样式、格式调整
```

例如：

```text
feat: 新增社团活动页面
fix: 修复移动端页面显示问题
docs: 更新项目维护说明
style: 优化首页布局
```

这些 Commit 类型和示例与项目现有开发规范保持一致。

---

### 3. 提交 Pull Request

完成开发并进行基本测试后，将自己的开发分支提交 Pull Request（PR）。

**PR 的目标分支统一为 `main`。**

提交 PR 时，请简单说明：

* 这次修改做了什么
* 修改了哪些内容
* 是否进行了测试
* 是否存在需要注意的地方
* 如果是页面修改，可以附上截图

之后等待其他维护者进行 Review 即可。

> **参与者不需要关心 PR 最后如何合并。**
>
> 提交 PR 后，维护者会负责后续的审核与合并。

---

## 🔍 PR 审核主要看什么？

维护者 Review 时通常会关注：

1. 功能是否符合预期
2. 页面或代码是否容易理解
3. 是否存在明显 Bug
4. 是否影响其他功能
5. 是否存在安全问题
6. 是否存在不必要的代码或调试信息
7. 是否误提交 `.env`、密钥等敏感信息
8. 修改是否保持项目整体风格统一

项目原有开发规范也将代码逻辑、可读性、边界情况、安全、性能以及敏感文件检查列为主要 Review 项目。

## ⚠️ 开发时请注意

### 不要直接修改 `main`

`main` 是项目的主分支，应始终保持可以正常运行。

```text
main
 ├── feature/xxx
 ├── feature/xxx
 ├── fix/xxx
 └── docs/xxx
```

所有开发工作请在自己的分支中完成，最后通过 PR 合并。

### 不要提交敏感信息

请不要将以下内容提交到 GitHub：

```text
.env
API Key
密码
Token
个人隐私信息
本地配置文件
大型构建产物
```

### 一个分支尽量只做一件事

例如：

```text
feature/activity-page
```

就主要负责“活动页面”。

不要同时：

```text
修改首页
+ 重构后端
+ 更新 README
+ 修复登录 Bug
```

这样会让代码 Review 和后续维护变得困难。

## 📋 PR 模板

提交 PR 时，可以直接使用下面的模板：

```markdown
## 简述

<!-- 一句话说明本次修改的目的 -->

## 改动内容

- 
- 
- 

## 自测

- [ ] 本地可以正常启动
- [ ] 功能符合预期
- [ ] 无明显控制台报错
- [ ] 没有提交 API Key、密码等敏感信息
- [ ] 新增功能已经进行基本测试

## 风险点

<!-- 是否可能影响其他功能？是否存在数据库、接口等变更？ -->

无风险，不影响现有功能。

## 截图

<!-- 如果修改了前端页面，建议附上修改前/修改后的截图 -->

## 关联 Issue

<!-- 如果有对应 Issue，可以填写，例如： -->

Closes #123
```

这个模板保留了项目原维护规范中的“改动内容、自测、风险点、截图、Issue 关联”等核心项目。
